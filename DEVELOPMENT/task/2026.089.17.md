Yes. This is the right point to design the share-trading data model **before** adding CommSec, CMC Invest, Stake, IBKR, Webull, Moomoo, Superhero, nabtrade, etc.

Your September architecture review already identified this as the next major data phase: keep `Provider` as the parent concept, introduce `ProviderOffering`, then structure products, markets, fees, features, holdings and regulatory relationships beneath the offering. It also correctly identified brokerage, FX, market access and CHESS/custody as data that needs to become first-class rather than arbitrary provider facts.

I would refine that proposal slightly now that we're designing the actual Prisma architecture.

# 1. The fundamental model

I recommend this hierarchy:

```text
Provider
│
├── ProviderLegalEntity
│   └── RegulatoryAuthorisation
│
├── ProviderOffering
│   │
│   ├── OfferingProduct
│   ├── OfferingMarket
│   ├── OfferingFee
│   ├── OfferingFeature
│   ├── OfferingHolding
│   ├── OfferingAccountType
│   └── OfferingOrderType
│
├── ProviderFact
├── ProviderSource
├── ProviderProsCons
├── ArticleProvider
│
└── AffiliatePartnership
```

The most important distinction is:

```text
Provider ≠ Offering ≠ Product
```

For example:

```text
CMC Markets
    Provider / brand
        │
        ├── CMC Invest
        │      ProviderOffering
        │
        │      ├── AU shares
        │      ├── International shares
        │      ├── ETFs
        │      ├── Options
        │      ├── mFunds
        │      ├── ASX
        │      ├── NYSE
        │      ├── NASDAQ
        │      ├── brokerage fees
        │      ├── FX fee
        │      └── holding structure
        │
        └── CMC Markets CFD
               ProviderOffering

               ├── CFDs
               ├── Forex
               ├── indices
               └── different fees/regulatory scope
```

This distinction is not theoretical. CMC's current Australian investing product supports Australian shares/ETFs, international shares/ETFs, options and mFunds, each with materially different pricing. ([CMC Markets][1])

That means putting everything directly on `Provider` will eventually produce ambiguous data.

Your review already established that the existing architecture has valuable provider-level concepts—facts, fees, features, regulations, assets, sources and partnerships—and explicitly recommends preserving `Provider` as the parent.

# 3. Introduce `ProviderOffering`

This is the most important Prisma change.

I recommend something close to:

```prisma
model ProviderOffering {
  id          String @id @default(cuid())

  providerId  String
  provider    Provider @relation(
    fields: [providerId],
    references: [id],
    onDelete: Cascade
  )

  name        String
  slug        String

  offeringType OfferingType

  description String? @db.Text

  jurisdiction String?

  active       Boolean @default(true)
  noIndex      Boolean @default(false)

  verificationStatus VerificationStatus @default(UNVERIFIED)
  lastVerifiedAt     DateTime?

  products     OfferingProduct[]
  markets      OfferingMarket[]
  fees         OfferingFee[]
  features     OfferingFeature[]
  holdings     OfferingHolding[]
  accountTypes OfferingAccountType[]
  orderTypes   OfferingOrderType[]

  sources      OfferingSource[]

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@unique([providerId, slug])
  @@index([offeringType])
  @@index([providerId])
}
```

And:

```prisma
enum OfferingType {
  SHARE_TRADING
  CRYPTO_EXCHANGE
  FOREX
  CFD
  OPTIONS
  FUTURES
  MULTI_ASSET
  WALLET
  OTHER
}
```

For your immediate project, the important ones are:

```text
SHARE_TRADING
CRYPTO_EXCHANGE
MULTI_ASSET
```

Don't overbuild the forex/CFD architecture yet.

# 5. Products should become relational data

Your review proposed structured product types rather than accumulating booleans.

I agree.

```prisma
enum InvestmentProductType {
  AU_SHARES
  INTERNATIONAL_SHARES
  ETF
  OPTIONS
  FOREX
  CFD
  CRYPTO
  BONDS
  MANAGED_FUNDS
  FUTURES
  WARRANTS
  MFUNDS
  OTHER
}

model OfferingProduct {
  id String @id @default(cuid())

  offeringId String
  offering   ProviderOffering @relation(
    fields: [offeringId],
    references: [id],
    onDelete: Cascade
  )

  productType InvestmentProductType

  available Boolean?

  notes String? @db.Text

  verificationStatus VerificationStatus @default(UNVERIFIED)
  sourceUrl          String?
  verifiedAt         DateTime?

  @@unique([offeringId, productType])
  @@index([productType])
}
```

This lets you query:

```ts
where: {
  products: {
    some: {
      productType: "ETF",
      available: true
    }
  }
}
```

instead of:

```text
supportsShares
supportsETF
supportsOptions
supportsBonds
supportsForex
supportsCrypto
...
```

# 8. `OfferingFee` should know what the fee applies to

I recommend:

```prisma
model OfferingFee {
  id String @id @default(cuid())

  offeringId String
  offering   ProviderOffering @relation(
    fields: [offeringId],
    references: [id],
    onDelete: Cascade
  )

  feeType ProviderFeeType

  label String

  valueType FeeValueType

  percentage Decimal? @db.Decimal(12, 6)
  fixedAmount Decimal? @db.Decimal(18, 6)
  currency String?

  minimumFee Decimal? @db.Decimal(18, 6)
  maximumFee Decimal? @db.Decimal(18, 6)

  displayValue String
  description  String? @db.Text

  market      MarketCode?
  productType InvestmentProductType?

  tradeMin Decimal? @db.Decimal(18, 2)
  tradeMax Decimal? @db.Decimal(18, 2)

  jurisdiction String?

  verificationStatus VerificationStatus @default(UNVERIFIED)
  sourceUrl          String?
  verifiedAt         DateTime?

  effectiveTo   DateTime?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([offeringId, feeType])
  @@index([market])
  @@index([productType])
}
```

Now you can model real pricing.

# 9. Example: CMC Invest

CMC currently advertises Australian-share pricing where the first buy under $1,000 in a security per day is $0, while other standard Australian buy/sell orders are $11 or 0.10%, whichever is greater. It separately advertises $0 brokerage for selected international markets, while a 0.60% FX spread applies to international orders. ([CMC Markets][1])

You need to represent these as separate records:

```text
CMC Invest
│
├── BROKERAGE
│   market = ASX
│   condition = first buy under $1,000/security/day
│   value = $0
│
├── BROKERAGE
│   market = ASX
│   value = $11 OR 0.10%
│
├── BROKERAGE
│   market = NYSE/NASDAQ
│   value = $0
│
└── FX_CONVERSION
    international orders
    value = 0.60%
```

Trying to store:

```text
brokerageFee = "$0"
```

would be materially misleading.

# 10. Fee conditions therefore deserve structure

Eventually I would go one step beyond the model above:

```prisma
model OfferingFeeTier {
  id String @id @default(cuid())

  feeId String
  fee   OfferingFee @relation(
    fields: [feeId],
    references: [id],
    onDelete: Cascade
  )

  minTradeValue Decimal?
  maxTradeValue Decimal?

  minVolume Decimal?
  maxVolume Decimal?

  fixedAmount Decimal?
  percentage  Decimal?

  minimumFee Decimal?
  maximumFee Decimal?

  conditionText String?

  sortOrder Int @default(0)
}
```

Then:

```text
OfferingFee
    Australian share brokerage

OfferingFeeTier
    $0–$1,000 → special condition
    otherwise → $11 / 0.10%
```

This also helps Interactive Brokers because its current US pricing has fixed and tiered plans, per-share commissions, minimum order charges and volume tiers. ([Interactive Brokers Australia Pty. Ltd.][3])

That cannot be represented reliably by one `percentage` field.

# 11. CHESS/custody absolutely needs first-class data

This is one of the strongest parts of the earlier proposal.

ASX explains that a CHESS-sponsored holder is registered in CHESS as the owner of securities, and the holding is associated with a HIN. ([Australian Securities Exchange][4])

Therefore:

```prisma
enum HoldingStructureType {
  CHESS_SPONSORED
  CUSTODIAL
  ISSUER_SPONSORED
  DIRECT_REGISTRATION
  MIXED
  NOT_APPLICABLE
  UNKNOWN
}
```

Then:

```prisma
model OfferingHolding {
  id String @id @default(cuid())

  offeringId String
  offering   ProviderOffering @relation(
    fields: [offeringId],
    references: [id],
    onDelete: Cascade
  )

  holdingType HoldingStructureType

  market MarketCode?

  hinSupported Boolean?

  description String? @db.Text

  verificationStatus VerificationStatus @default(UNVERIFIED)

  sourceUrl  String?
  verifiedAt DateTime?

  @@index([offeringId])
  @@index([holdingType])
}
```

Why include `market`?

Because a provider could use:

```text
ASX
→ CHESS sponsored

US shares
→ custodian structure
```

One global:

```ts
chessSponsored: true;
```

is not sufficient.

# 17. Why regulatory scope matters

You have already encountered this problem with crypto.

For example:

```text
Provider has AFSL
```

does **not** necessarily mean:

```text
Every product supplied by that brand is
provided under that AFSL.
```

The same issue becomes even more important with multi-product brokers.

Therefore I would add an optional linkage:

```prisma
model OfferingAuthorisation {
  offeringId      String
  authorisationId String

  offering      ProviderOffering
  authorisation RegulatoryAuthorisation

  scopeNotes String? @db.Text

  @@id([offeringId, authorisationId])
}
```

Now the database can say:

```text
CMC Markets
     │
     ├── Legal entity
     │      └── AFSL XXXXX
     │
     └── CMC Invest
             └── linked regulatory authorisation
```

rather than displaying a generic regulatory badge with unclear scope.

Then see where the schema breaks.

### Phase B — Australian ownership/account concepts

Add:

```text
OfferingHolding

OfferingOrderType
```

Validate CHESS/custodial differences carefully. ASX's current documentation supports treating CHESS sponsorship/HIN as a meaningful ownership/settlement concept rather than a generic feature. ([Australian Securities Exchange][5])

### Phase C — Regulatory normalization

Add:

```text
ProviderLegalEntity

```

Migrate regulatory facts gradually.

### Phase D — Consolidation

Only after the new system is working:

```text
ProviderFee
        ↓

        ↓
OfferingFeature

Provider-level product facts
        ↓
OfferingProduct
```

Some provider-level models may remain useful permanently.

# 27. One important change from our earlier discussion

Previously we talked about moving practically everything underneath `ProviderOffering`.

I would now be a little more conservative.

Keep genuinely corporate facts at `Provider`:

```text
Founded
Brand
Website
Headquarters
Parent company
About
General source documents
```

Put product-specific facts at `ProviderOffering`:

```text
Brokerage
FX fees
Markets
Products
CHESS/custody
Order types
Platform features
Account types
```

Put legal facts at `ProviderLegalEntity`:

```text
Legal name
ABN
ACN
AFSL
Authorisations
Regulatory scope
```

That gives you a clean three-level separation:

```text
BRAND
Provider
   │
   ▼
PRODUCT
ProviderOffering
   │
   ▼
LEGAL
ProviderLegalEntity / Authorisation
```

This is substantially safer than trying to make one giant `Provider` record describe all three concepts.
