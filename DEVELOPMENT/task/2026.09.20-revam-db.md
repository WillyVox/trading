## The core problem

Your application currently uses `Provider` to mean two different things:

```text
CRYPTO

Provider
└── CoinSpot
    ├── fees
    ├── features
    ├── assets
    └── comparison data


SHARE TRADING

Provider
└── CMC Markets
    └── ProviderOffering
        └── CMC Invest
            ├── fees
            ├── markets
            ├── products
            ├── custody
            └── comparison data
```

That asymmetry is the fundamental issue.

For crypto, the **provider/company is also the comparable product**.

For share trading, the **provider/company owns a comparable product/offering**.

As a result, `ProviderType` currently tries to answer several different questions:

```prisma
enum ProviderType {
  CRYPTO_EXCHANGE
  BROKER
  MULTI_ASSET_BROKER
  TRADING_PLATFORM
  WALLET_PROVIDER
  OTHER
}
```

But those values are not really equivalent concepts.

`BROKER` describes an organisation/business role.

`TRADING_PLATFORM` describes a product/service.

`CRYPTO_EXCHANGE` can mean either a company or its service.

`WALLET_PROVIDER` again describes something different.

That ambiguity leaks into your service layer and pages.

# A concrete bug already exists

Your `/crypto/exchanges` page currently does:

```ts
const { items } = await getProviders();
```

And `getProviders()` only filters when a type is explicitly supplied:

```ts
where: opts.providerType ? { providerType: opts.providerType } : undefined;
```

So `/crypto/exchanges` can return:

```text
CoinSpot
Swyftx
Kraken
CommSec's parent Provider
CMC Markets
Interactive Brokers
Stake
...
```

even though every result is linked as:

```text
/crypto/exchanges/{slug}
```

This is exactly the mixing problem you're seeing.

You already fixed the same issue manually in `/compare`:

```ts
getProviders({
  providerType: ProviderType.CRYPTO_EXCHANGE,
});
```

but the architecture still allows another page to forget the filter.

There is another similar weakness in:

```ts
getComparisonPool("crypto-exchange");
```

because it ultimately executes:

```ts
getProviders({ pageSize: 100 });
```

without explicitly constraining the type.

So the problem isn't simply "one page forgot a filter."

**The service API makes the wrong query easy to write.**

# The comparison engine should know the domain before querying

Today your dynamic comparison resolver essentially asks:

```text
Try these slugs as Providers.

Did they all match?

Yes → crypto.

Otherwise try Offerings.

Did they all match?

Yes → share trading.
```

That's clever as a transitional mechanism, but I wouldn't keep it as the final architecture.

The URL itself should identify the domain.

For example:

```text
/compare/crypto/coinspot-vs-swyftx

/compare/share-trading/commsec-vs-stake
```

or:

```text
/compare/crypto-exchanges/coinspot-vs-swyftx

/compare/trading-platforms/commsec-vs-stake
```

Then:

```ts
resolveComparison({
  domain: "crypto-exchange",
  slugs,
});
```

rather than trying both databases and inferring what the user meant.

### Benefits

You eliminate:

```text
slug collisions
mixed-domain queries
unnecessary DB calls
ambiguous routing
accidental cross-category suggestions
future category conflicts
```

And adding CFDs later becomes trivial:

```text
/compare/cfd-platforms/...
```

# I would also change the service philosophy

Avoid generic functions like:

```ts
getProviders();
```

for public-facing pages.

They're too dangerous.

Instead expose intent-specific queries:

```text
getCryptoExchanges()
getCryptoExchangeBySlug()

getShareTradingPlatforms()
getShareTradingPlatformBySlug()

getCryptoComparisonSubjects()
getShareTradingComparisonSubjects()
```

Internally they can share repositories.

The difference is important.

Bad:

```ts

```

The caller must remember what filtering is required.

Better:

```ts

```

The service guarantees the invariant.

A developer can't accidentally render CommSec on `/crypto/exchanges`.

# Migration strategy

I would **not** perform a giant schema rewrite.

Your share-trading implementation is already reasonably close to the target.

I'd migrate incrementally:

1. Keep `Provider` as the organisation/brand entity.
2. Make `ProviderOffering` the canonical comparable entity.
3. Add `CRYPTO_EXCHANGE` to `OfferingType`.
4. Create offerings for existing crypto providers.
5. Move crypto-specific comparison data gradually from `Provider*` structures into offering-level structures.
6. Introduce domain-specific catalog services.
7. Make every public list require an explicit domain.
8. Change the comparison resolver to domain-first routing.
9. Migrate crypto detail pages to offering-backed data.
10. Deprecate `ProviderType` once nothing important relies on it.

During migration you can support:

```text
Legacy Provider crypto data
        ↓
adapter
        ↓
ComparisonSubject
```

and:

```text
New Offering data
        ↓
adapter
        ↓
ComparisonSubject
```

so the UI does not need a big-bang rewrite.

# What I'd fix immediately vs later

There are two levels.

**Immediate safety fix:** explicitly scope `/crypto/exchanges` and `getComparisonPool("crypto-exchange")` to `CRYPTO_EXCHANGE`, then audit every `getProviders()` call. This stops today's data leakage with very little risk.

**Architectural migration:** make `ProviderOffering` the universal comparison subject and gradually move crypto onto it.

I recommend doing both, in that order.

## What moves to Offering vs. what stays on Provider

The CoinSpot seed makes this decision non-trivial — its `facts[]` array mixes two genuinely different things:

- **Brand-level, stays on `Provider`**: `"Operating entity: Casey Block Services Pty Ltd (ACN 619 574 186), trading as CoinSpot"` — this is a fact about the legal entity, exactly like `CommSec`'s parent (`"Commonwealth Bank of Australia"`) stays on `Provider` today.
- **Product-level, moves to `Offering`**: `"AUD Support"`, `"Platform Type"`, all of `ProviderFee`, all of `ProviderFeature`, all of `ProviderAsset` — these describe what CoinSpot-the-product does, not who Casey Block Services is.

So this isn't a mechanical table rename — each seed's `facts[]` array needs a per-row judgment call about which side of the split it belongs on. `ProviderRegulation` and `ProviderProsCon`/`ProviderSource` I'd leave on `Provider` by default (regulation attaches to the legal entity; sources/pros-cons are more debatable but lower-stakes to get "wrong" first pass — easy to move later).

## Schema additions needed

- **`OfferingFeature`** — mirrors `ProviderFeature` (reuse the existing `ProviderFeatureType` enum; it's already crypto-specific — `STAKING`, `OTC_DESK`, `AUD_DEPOSITS`, etc. — no need for a new enum).
- **`OfferingAsset`** — mirrors `ProviderAsset`, joins `ProviderOffering` ↔ `CryptoAsset`.
- **Crypto's fee shape does _not_ fit the existing `OfferingFee` model.** That table is purpose-built for broker rate schedules — `FeeCategory`/`FeeCalculationBasis`/`FeeChannel`/`OfferingFeeTier` model tiered brokerage that varies by market and settlement channel. CoinSpot's fees are flat/percentage, no tiers, no channel. Forcing them into that shape would be exactly the "leaky abstraction" the codebase's own comments warn against elsewhere (`compare/types.ts`: _"crypto and share trading dimensions should not be forced into one vocabulary"_). I'd add a second, crypto-shaped fee table — practically, just retarget the existing `ProviderFee` model from `providerId` to `offeringId` and keep its shape (`ProviderFeeType`, `FeeValueType`, `percentage`/`fixedAmount`) as-is.

## Sequencing

1. **Fix the `ArticleProvider`/`RelatedProviders` domain-blind link now, independent of everything else.** It's cheap, it's already a live landmine (guides can tag a broker's `Provider` row and get a `/crypto/exchanges/` link), and it doesn't block or get blocked by the offering migration.
2. **Additive schema migration**: add `OfferingFeature`, `OfferingAsset`, retarget `ProviderFee`→offering-scoped (new table, don't touch the existing one yet — old and new coexist during migration).
3. **Create a `ProviderOffering` row per crypto `Provider`**, type `CRYPTO_EXCHANGE`, splitting each seed's `facts[]` per the brand/product rule above.
4. **Backfill** offering-scoped fee/feature/asset rows from the existing `ProviderFee`/`ProviderFeature`/`ProviderAsset` data (a script, not hand-written seeds — you don't want to re-type CoinSpot's sourced fees).
5. **Repoint the crypto compare/catalog layer** (`providers/compare.ts`, `crypto/service.ts`, the `/crypto/exchanges` pages) onto the offering-scoped tables, using the same domain-explicit query pattern share trading already has.
6. **Repoint affiliate CTA resolution.** Today `AffiliateLink.partnerSlug` == `Provider.slug` by convention. Since your crypto offerings will be 1:1 with their parent provider, resolving via `offering.provider.slug` keeps this working unchanged — worth a deliberate comment in code so it doesn't look accidental.
7. **Deprecate the old `Provider`-level fee/feature/asset tables** for crypto once everything reads from the new ones — drop the migration path, not the moment it works.
