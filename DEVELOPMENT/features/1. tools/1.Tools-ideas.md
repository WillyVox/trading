For Trading Guide, I prefer Tools over Calculators because several of the strongest ideas aren't calculators at all: CHESS/custody explorer, fee breakdowns, terminology explainers, provider-data explorer, market-access finder, and comparison builders. “Calculators” can then be one category within /tools.

Your requirements already emphasize that users should understand costs, limitations, terminology, sources, verification dates, and what to research next. That maps almost perfectly to an interactive-tools strategy.

2. The important architectural principle

I would not build ten independent calculators containing hard-coded CommSec/CMC/Stake fee logic.

That will become a maintenance disaster.

Instead:

                 VERIFIED DATABASE
                       │
        ┌──────────────┼───────────────┐
        │              │               │
     OFFERING        MARKET           FEES
        │              │               │
        └──────────────┼───────────────┘
                       ↓
                FEE/RULE ENGINE
                       ↓
              SCENARIO ENGINE
                       ↓
       ┌───────────────┼────────────────┐
       ↓               ↓                ↓
 Brokerage         FX calculator     Comparison
 calculator                           scenarios

The database is the source of truth.

The calculators are simply different interfaces over the same verified facts.

This is crucial.

If CommSec changes a fee, you should update one structured fact and have the provider profile, comparison table, brokerage calculator and scenario tool all update consistently.

19. Build one shared calculation engine

I'd introduce something conceptually like:

src/lib/calculators/

    types.ts

    brokerage/
        engine.ts
        rules.ts
        explain.ts

    fx/
        engine.ts
        explain.ts

    scenarios/
        engine.ts

    validation.ts

But don't create provider-specific files like:

commsec-calculator.ts
stake-calculator.ts
cmc-calculator.ts

unless a genuinely provider-specific published rule cannot be represented generically.

Prefer:

calculateFee({
  fee,
  amount,
  market,
  transactionType,
  pricingPlan,
});

returning something richer than a number:

{
  amount: 10,
  currency: "AUD",

  rule: {
    type: "TIERED",
    description: "...",
  },

  calculation: {
    baseAmount: 2000,
    percentage: null,
    minimum: null,
  },

  source: {...},

  verifiedAt: ...,

  assumptions: [...],

  exclusions: [...]
}

The explanation is as important as the result.

20. A calculator should refuse to fake precision

Suppose your database knows:

Brokerage: $0
FX: UNKNOWN
Spread: VARIABLE

Do not calculate:

Total cost = $0

Return:

Estimated brokerage
$0

Other costs
FX conversion — information unavailable
Spread — variable

A complete transaction cost cannot be calculated
from the verified information currently available.

That will make Trading Guide more trustworthy.
