## Milestone proposal: GA4 + Search Console

The codebase is in a good position for this milestone. In particular, you already have:

- a first-party affiliate redirect and click-recording system at `/go/[partner]`
- placement/campaign attribution for affiliate clicks
- strong canonical/sitemap/robots foundations
- an existing cookie notice
- a privacy policy explicitly documenting current tracking behaviour
- production CSP controls
- production-readiness gates

That means we should **add analytics as a measurement layer**, rather than restructure your existing affiliate system.

# 1. What I found in the current code

### No GA4 currently exists

I found no GA4, `gtag`, Google Tag Manager, tracking pixel, or equivalent analytics integration.

Your Privacy Policy correctly says:

> “We don't currently use analytics, advertising, or tracking-pixel tools…”

And `CookieNotice.tsx` explicitly says the current notice is an **acknowledgement rather than a consent mechanism**.

This is actually useful because we can introduce GA4 cleanly instead of having to repair an existing implementation.

### The existing cookie UI must change

Currently the user gets essentially:

**Cookies, kept minimal**

`OK, got it` | `Cookie details`

Once GA4 exists, that statement becomes inaccurate.

Your own source comments already anticipated this and say that adding analytics should change the banner into:

**Accept / Reject non-essential / Manage**

That is exactly the direction I recommend.

### Affiliate tracking is already architecturally sound

Your current flow is approximately:

```text
User
   ↓
Trading Guide CTA
   ↓
/go/etoro?placement=compare
   ↓
AffiliateLink lookup
   ↓
AffiliateClick stored in PostgreSQL
   ↓
307 redirect
   ↓
Partner affiliate URL
```

This should remain.

GA4 becomes an **additional behavioural measurement**, not the affiliate ledger:

```text
                       ┌── GA4: affiliate_click
User → CTA → /go/... ──┤
                       └── PostgreSQL AffiliateClick
                                      ↓
                              Partner website
```

The database remains the reliable source for your own click reporting.

GA4 answers different questions:

> Where did the visitor come from?
> What did they read?
> What did they compare?
> Which pages eventually produced partner clicks?

That distinction is important.

# 3. Consent model

Google Consent Mode v2 supports `analytics_storage`, `ad_storage`, `ad_user_data`, and `ad_personalization`. Google specifically recommends establishing consent defaults before tags use them. ([Google Developers][1])

For Trading Guide I would initially set:

```text
analytics_storage   DENIED
ad_storage          DENIED
ad_user_data        DENIED
ad_personalization  DENIED
```

When the visitor accepts analytics:

```text
analytics_storage   GRANTED
ad_storage          DENIED
ad_user_data        DENIED
ad_personalization  DENIED
```

Notice what I'm deliberately **not** recommending:

```text
Accept all → enable advertising everything
```

You currently need website analytics, not behavioural advertising.

Keep advertising consent off until there is an actual business requirement for Google Ads/remarketing.

# 4. Basic vs advanced Consent Mode

Google currently distinguishes **Basic** and **Advanced** Consent Mode.

With Basic Consent Mode, Google tags are blocked before consent. With Advanced Consent Mode, tags can load under denied consent and send limited cookieless measurements. ([Google Developers][2])

For this first implementation I recommend:

### **Basic Consent Mode**

Meaning:

```text
First visit
     ↓
No GA request
No analytics cookie
     ↓
Banner displayed
     │
 ┌───┴────┐
Reject   Accept
  │         │
  ▼         ▼
nothing   load GA4
           ↓
        analytics
```

This is simpler to reason about and easier to explain to users.

We can revisit advanced modelling later if there is a compelling business reason.

# 10. Tracking plan

This is where the milestone becomes commercially useful.

I would **not** track every click.

That produces noisy GA data.

Instead, start with meaningful business/product events.

### Tier 1 — launch events

| Event                | Purpose                    |
| -------------------- | -------------------------- |
| `page_view`          | traffic                    |
| `affiliate_click`    | outbound commercial intent |
| `comparison_created` | comparison engagement      |
| `provider_view`      | provider interest          |
| `tool_used`          | calculator engagement      |
| `search`             | site-search usage          |
| `sign_up`            | account creation           |

Google already defines recommended events including `search`, `select_content`, `sign_up`, and `generate_lead`; using standard events where they genuinely match the behaviour makes GA reporting easier. ([Google Developers][4])

# 18. Search Console architecture

For Search Console I recommend creating a **Domain property** for your production domain.

A Domain property covers protocols and subdomains; Google requires DNS verification for this property type. ([Google Help][7])

Conceptually:

```text
tradingguide.com.au
│
├── https://tradingguide.com.au
├── http://tradingguide.com.au
├── www.tradingguide.com.au
└── future subdomains
```

all belong to one Search Console Domain property.

This is preferable to only:

```text
https://tradingguide.com.au/
```

# 22. CSP needs modification

This is one of the main technical findings from the audit.

Your production CSP currently effectively says:

```text
script-src 'self'
connect-src 'self'
```

GA4 requires access to Google endpoints.

Google's CSP guidance says GA without Ads features needs allowances including `www.googletagmanager.com` for scripts and Google Analytics/Google endpoints for network/image connections. ([Google Developers][9])

So `next.config.mjs` will require a carefully scoped modification.

We should **not** simply do:

```text
script-src *
connect-src *
```

just to make Analytics work.

Instead we'll allow only the necessary endpoints.

And because your project already has:

```text
Content-Security-Policy-Report-Only
→ verify
→ CSP_ENFORCED_AND_VERIFIED=true
```

we should use that existing workflow.

That's an excellent fit.

# 24. Australian privacy consideration

There is an important nuance here.

I wouldn't tell you:

> “Australian law always requires cookie consent.”

That's too simplistic.

OAIC's current guidance focuses on whether tracking technologies collect personal/sensitive information, transparency, purpose, minimisation, disclosure and overseas handling. OAIC specifically recommends due diligence and data minimisation for third-party tracking technologies. ([OAIC][11])

Because Trading Guide could eventually have visitors from multiple jurisdictions, and because an explicit choice gives you a cleaner privacy posture anyway, I recommend the **opt-in analytics design** regardless.

Your existing legal gate should remain:

```text
LEGAL_CONTENT_APPROVED=true
```

only after your final privacy wording has actually been reviewed/approved.

# 28. Recommended implementation phases

I would break this milestone into **six small implementation phases**:

**Phase A — analytics foundation:** environment configuration, analytics types/helper, GA loader, production-only safeguards and tests.

**Phase B — consent:** replace acknowledgement banner with real preferences, persistent versioned consent state, Accept/Reject/Manage, footer preference control, and Consent Mode integration.

**Phase C — GA4:** page views, SPA navigation validation, privacy configuration and DebugView/Tag Assistant testing.

**Phase D — business events:** affiliate clicks, comparisons, calculator use, provider/content engagement and signup. Use Google's recommended events where they semantically fit and custom events where Trading Guide has a domain-specific action.

**Phase E — Search Console:** Domain property, DNS verification, sitemap submission, canonical/index inspection, GA association where useful.

**Phase F — compliance + release:** privacy/cookie wording, CSP report-only testing, PII audit, production validation, consent tests, GA DebugView verification and production-readiness gate updates.

# 30. One change I would make to the original milestone definition

Originally we described it as:

> GA4 + Google Search Console

I would formally rename it:

## **Milestone 5 — Measurement, Search Visibility & Consent**

with four deliverables:

```text
5.1 Consent & privacy foundation
5.2 Google Analytics 4
5.3 Business/conversion measurement
5.4 Google Search Console
```

That better reflects what we're actually building.

The critical principle is:

> **GA4 measures behaviour.
> Trading Guide's database records affiliate business events.
> Search Console measures Google discovery.
> Consent controls whether optional analytics operates.**

Keeping those responsibilities separate will give you a much cleaner system as Trading Guide grows.

Google requires Analytics implementations to avoid PII, and its current guidance supports Consent Mode v2; OAIC guidance also stresses transparency and minimisation around third-party tracking. ([Google Help][5])

**I recommend approving this architecture and moving next to implementation of 5.1 + 5.2 together**—the environment/analytics foundation and new consent system—before instrumenting individual business events. That avoids adding tracking calls before the privacy foundation is capable of controlling them.
